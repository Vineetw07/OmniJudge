## 3. Adversarial Challenge & Stress-Testing

### Challenge 1: Tailwind v3 Opacity Modifiers on OKLCH Colors
- **Assumption Challenged**: Classes like `hover:bg-primary/80` or `bg-destructive/10` in `button.tsx` and `badge.tsx`. In Tailwind v3, `/alpha` modifiers require `<alpha-value>` placeholder inside `rgb()` or `hsl()`. When variables are defined as `oklch(0.205 0 0)` without `<alpha-value>`, Tailwind v3 outputs the variable as-is or cannot parse the alpha slash.
- **Attack Scenario**: Calling `<Button variant="default">` and hovering might fail to apply the 80% opacity hover state.
- **Blast Radius**: Minor visual styling nuance on hover; does not crash runtime, does not break build, and does not cause PostCSS errors.
- **Mitigation/Recommendation**: For future phases when refining theme colors, if alpha modifiers are needed, either define CSS variables as OKLCH channels (e.g. `--primary: 0.205 0 0`) or use `color-mix(in oklch, var(--primary), transparent 20%)` as already done for secondary button variant (`color-mix(in_oklch,var(--secondary),var(--foreground)_5%)`).

### Challenge 2: Base UI Primitives vs Radix UI Class Conventions
- **Assumption Challenged**: shadcn components typically use Radix UI primitives (`data-[state=open]`). The installed components use `@base-ui/react` primitives (`data-open`, `data-closed`).
- **Attack Scenario**: Interactive dropdowns or dialogs failing to open/close or animate smoothly if variants are mismatched.
- **Verification**: `tailwind.config.ts` registered custom variants supporting both `data-open` and `data-[state="open"]`:
  `addVariant("data-open", ['&:where([data-state="open"])', '&:where([data-open]:not([data-open="false"]))']);`
- **Result**: PASS. Both conventions are supported.
